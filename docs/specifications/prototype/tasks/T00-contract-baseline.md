# T00 — Establish the contract baseline and fictional walkthrough

Status: not started. Type: design/fixtures. Prerequisites: [product direction](../../product-direction.md) and [prototype plan](../README.md).

## Outcome

Give implementation agents one concrete, internally consistent example of the complete workflow, plus shared field definitions and behavior cases. Keep the work small enough to show the owner before substantial implementation.

## Ownership and deliverables

- Own revisions to [data contracts](../data-contracts.md), [decision register](../decisions.md), and the initial CLI example in [architecture](../architecture.md).
- Add fictional artifact examples under `test/fixtures/prototype/contracts/` with a README explaining expected relationships; these paths do not exist yet.
- Add a three-level illustrative report under `docs/specifications/prototype/examples/`, visibly labeled as fictional and not generated by an implemented collector.
- Record the initial Ubuntu release/architecture for live trials when available. Lack of a live target does not block fictional fixture work.

## Work steps

1. Inventory agreed requirements versus experimental choices. Keep E01–E10 as proposed unless evidence or owner feedback changes them.
2. Define complete envelopes, required/optional fields, enum values, UTC timestamp representation, ordering, and unknown-version behavior.
3. Freeze an initial normalization specification for identities and fact fingerprints, including encoding and hashing. Write a fixed example with expected output to avoid cross-agent divergence.
4. Define sufficient advance expectations for a port example and a sudo example; show an insufficient expectation that cannot automatically apply.
5. Construct a fictional target with a public HTTP endpoint, a local-only endpoint awaiting judgment, and a sudo rule plus an unsupported policy construct.
6. Create first-run, unchanged-repeat, changed-owner/context, explicit human reconfirmation, partial-collection, unmatched-assessment, and conflicting-assessment examples. Show how a user makes a new decision against changed facts without silently upgrading the old decision.
7. Produce the report walkthrough from these same facts. Make the explanation prompts relevant to public static content and external firewall restrictions without declaring either automatically safe.
8. Walk the example through P0 using [the trial guide](../../../user-guides/prototype-trials.md). Incorporate actual feedback; record unanswered questions explicitly.

## Boundaries

No live host collection, full JSON Schema framework, approval workflow, GUI, release work, or exhaustive sudo parser. A plain set of precise field definitions and representative fixtures is sufficient. Do not require the owner to decide every future product detail.

## Acceptance cases

- Given the first-run example, every report item traces to an observation and evidence entry; no human judgment appears as a tool observation.
- Given an advance entry without a previous snapshot, the expected application or re-review outcome is explicit.
- Given an unchanged item and a changed item, expected reuse differs and the previous rationale remains visible in both histories.
- Given no findings because collection failed, the sample summary cannot be mistaken for successful empty coverage.
- Given the same sample, report counts reconcile with item-level states and do not count stale acceptance as current acceptance.
- All JSON examples parse, all linked artifacts exist, and examples clearly declare fictional data.

## Handoff

Provide a contract revision identifier, examples, expected fingerprints, matching outcomes, and remaining questions. Notify T01–T06 of the baseline. Separate “reviewed by the owner” from “prepared by an agent.”
